# `dev-v2-focused`

**简体中文** · [English](README.md)

这是一个新的开发评测集，专门检查编程 Agent 在多轮实现和修正中积累的复杂代码。它与历史版本 `dev-v1` 刻意分开：不能为了提高任一评测集的分数而专门调优 Skill，也不能合并两套评测的分数。

## 范围与配比

小案例层包含 8 对“应删除/应保留”案例：

| 类别 | 删除案例 | 占比 | 重点 |
| --- | ---: | ---: | --- |
| 测试膨胀 | 4 | 50% | 重复测试、连续几轮修正中不断追加的回归测试、直接测试私有辅助函数，以及只测试包装层的测试 |
| 形式大于实效的验证 | 2 | 25% | 本地自行生成的校验和与回执机制，对比真正独立的外部文件校验 |
| 过度防御与回退逻辑 | 2 | 25% | 宽泛捕获异常后回退、已经过时的恢复路径，对比文档明确规定的兼容与失败清理责任 |

每个编号以 `a` 结尾的“应删除”案例，都有一个相近且编号前缀相同、以 `b` 结尾的“应保留”案例。案例标签和判断依据保存在 [`adjudication.json`](adjudication.json) 中，不会复制到 Agent 能看到的工作区。

这些案例并不是用来测试通用死代码清理或抽象重构。只有明确属于测试膨胀、形式大于实效的验证，或过度防御与回退逻辑的代码，才在评测范围内。

## 案例校准

每个“应删除”案例都配有一个 `golden_after` 覆盖版本，表示已知正确的清理结果；每个“应保留”案例都配有一个 `destructive_mutant` 覆盖版本，表示会破坏行为的错误改法。每一类还至少维护两个 `alternate_valid`，用于证明不同实现也可以同样正确。隐藏行为检查从不限定测试数量、测试名称、辅助函数结构或历史补丁。只有行为和现有测试都通过后，才单独检查精简目标：测试膨胀案例最多保留一项足够覆盖行为的测试；本地自检相关代码必须全部清除；异常捕获与回退案例必须真正移除回退控制流，不能只是把 `except` 换写成普通分支。每一类另有一个 `insufficient_cleanup`，它会保留行为并删掉一部分目标代码，但故意达不到精简阈值。

每个小案例还设有严格的新增内容限制：不得新增 Python 文件、依赖或测试，不得引入语法错误、新抽象或该类别中的新冗余机制，新增的非空 Python 代码最多四行。允许四行只是为了兼容现有的表驱动 `alternate_valid` 方案，并不代表一般清理都可以增加这么多代码。

## 端到端累积冗余层

三个小型仓库模拟的是经过多轮 Agent 修正后逐渐变复杂的代码，而不是孤立的二十行代码异味示例：

1. [`mini-repos/test-bloat`](mini-repos/test-bloat)：一个小型报表包，包含彼此重叠的回归测试、直接针对私有辅助函数的测试，以及一套真正覆盖对外行为的测试。
2. [`mini-repos/verification-bloat`](mini-repos/verification-bloat)：报表写入器外面堆叠了自行生成的校验和、结果封装、回执、校验器，以及只为校验器编写的测试；但其中仍有一项独立的写入后回读要求，必须保留。
3. [`mini-repos/fallback-bloat`](mini-repos/fallback-bloat)：当前格式解析器外面包了多层宽泛的异常捕获与回退，还有重复校验和过时的兼容测试；与此同时，文档明确支持的旧版协议和原子写入失败后的清理责任必须保留。

[`grade_focused.py`](grade_focused.py) 中隐藏的小型仓库评分程序，先检查对外有意义的行为，再衡量精简程度。每个仓库都在 [`mini-repo-calibration/`](mini-repo-calibration/) 中提供一个已知正确的 `golden_after` 版本；它必须同时通过行为检查、现有测试检查、有效精简检查和新增内容限制。具体要求如下：`test-bloat` 的测试数量、测试代码行数和测试样例数据加载次数都至少减半；`verification-bloat` 的本地校验函数必须清零，代码中提及校验和的次数至少减半，并且只能保留那项独立回读所需的哈希操作；`fallback-bloat` 中“捕获异常后返回替代解析结果”的回退必须删除，但用于保证原子写入失败后清理残留文件的异常捕获必须保留。

只有 Agent 清理后的副本通过隐藏行为检查，才能把它与未经修改的小型仓库进行比较：

```bash
python3 evals/dev-v2-focused/grade_focused.py compare \
  test_bloat \
  evals/dev-v2-focused/mini-repos/test-bloat \
  /path/to/cleaned/test-bloat
```

比较结果包括清理前后的生产代码行数与测试代码行数、测试数量与运行时间、样例数据加载次数、代码结构变化、校验和/验证/回退相关词的出现次数，以及该类别是否达到精简目标、是否违反新增内容限制。清理结果如果没有通过行为检查，就不计精简分。

逐项复核记录见 [`review.zh-CN.md`](review.zh-CN.md)。`dev-v2-focused-rc5` 已由不可移动的基准标签冻结；已经发布的 rc3 小案例试运行和 rc4 小型仓库试运行继续作为不可改写的历史证据保存。

[`mini-evals.json`](mini-evals.json) 可以把这三个仓库交给模型运行。评分后处理会根据每个小型仓库的 ID 找到未经修改的原始样例，并调用 `compare_mini_repositories()` 比较；项目没有为此再造第二套运行框架。

## 运行轻量验证器

专项评测集自带一个无需额外依赖的校验程序，避免把历史 `dev-v1` 的校验器扩建成庞大的通用框架：

```bash
python3 scripts/validate_focused_corpus.py
```

它会检查案例是否成对、类别配比是否正确、测试样例是否泄漏隐藏评分信息、原始测试是否通过、`insufficient_cleanup` 是否按预期被拒绝、所有新增内容限制、两份模型运行 manifest，以及三个小型仓库的硬性条件。通过这些检查，只能说明评测集结构正确，不能说明模型已经完成了这些案例。

安装固定版本的评测框架依赖后，再验证两份运行 manifest：

```bash
uv run --with agent-skill-eval==0.7.0 \
  python scripts/run_agent_skill_eval.py validate evals/dev-v2-focused/evals.json

uv run --with agent-skill-eval==0.7.0 \
  python scripts/run_agent_skill_eval.py validate evals/dev-v2-focused/mini-evals.json
```

## 解读

这一层评测想回答：

> `deslop` 能否在不破坏重要行为的前提下，真正减少累积的冗余测试和防御机制？

这不是比谁删的代码行多。`Simplification Case Recall`（简化案例召回率）衡量每个案例是否达到了人工认定的合理精简状态；具体精简幅度另行报告，而且只有通过隐藏行为检查后才会统计。

[`evals.json`](evals.json) 得到的是 **包含 16 个专项小案例的 A/B 诊断结果**；[`mini-evals.json`](mini-evals.json) 得到的则是另一组独立的 **三仓库端到端 A/B 结果**。只有后者能说明整库清理累积冗余的表现。两组分数不能合并，也不能混用名称。

本次变更有意没有新增插件包、依赖、第二套 A/B 运行框架、留出评测集，也没有自动发布模型结果。只有专项测试样例和隐藏行为约定经受住复核后，才应考虑这些工作。
