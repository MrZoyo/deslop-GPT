# 架构与设计取舍

简体中文 | [English](ARCHITECTURE.en.md) | [文档目录](README.md) | [项目首页](../README.md)

本文解释当前实现的行为、指标口径和信任边界。配置字段见[配置参考](CONFIGURATION.md)，
安装命令见[部署指南](DEPLOYMENT.md)。

## 目标与非目标

Cluster GPU Monitor 面向几台到几十台、没有统一调度器的自管 GPU 服务器。它优先解决：

- 不在目标节点安装 agent，通过中心机的既有 SSH 配置采集。
- 保留长期利用率，并把显存占用归属到操作系统用户名。
- 用一个小型自托管服务支持容量规划，而不是搭建完整遥测平台。

它不提供秒级告警、资源调度、配额、审计级身份映射或账单结算。上千节点和高频遥测也不是
SQLite 单机架构的目标场景。

## 数据流

```text
inventory.yaml + ~/.ssh/config
              │
              ▼
中心采集器 ── ssh <alias> bash -s ──► GPU 节点
              │                         nvidia-smi / amd-smi / rocm-smi
              │                         ps + /proc（不写远端文件）
              ▼
SQLite：维度表 + 原始样本 + 5 分钟/1 小时聚合
              │
              ▼
只读 FastAPI ──► 原生 HTML / JavaScript / 本地 ECharts
```

`inventory.yaml` 定义逻辑拓扑和稳定标识；地址、端口、账号、密钥与 `ProxyJump` 留在采集
账户的 `~/.ssh/config`。改变网络路径时不需要修改数据库关联键。

## 采集模型

每轮采集只处理 `active` 主机，并执行以下步骤：

1. 为整轮分配同一个 epoch 秒时间戳，使不同主机的样本可以对齐。
2. 在 `max_concurrency` 边界内，每台主机建立一次系统 OpenSSH 连接。
3. 通过 stdin 执行 `remote_probe.sh`，一次取回 GPU、进程、CPU、内存和 load。
4. 在中心机解析并校验输出，再以一个 SQLite 事务写入这一轮结果。
5. 单机失败只更新该机的采集状态，不阻断其他主机。

未指定 `vendor` 时，远端每轮依次探测 NVIDIA 与 AMD 工具；正常 NVIDIA 主机会额外执行一次
`nvidia-smi -L`。厂商已知且固定时应显式设置，以减少目标机上的 SMI 调用；留空适合厂商未知
或硬件可能更换的环境。NVIDIA 路径已有长期运行经验，AMD 解析器目前有构造样本测试，但仍缺
真实硬件闭环。

远端输出按不可信输入处理：SSH 有连接、总时长和字节上限；每台与每轮的 GPU/进程对象也有
数量上限。异常进程量可以被省略，同时保留 GPU 与主机指标并在采集状态中留下告警。

## 拓扑与生命周期

逻辑层级固定为“算力域 → 集群 → 主机 → 自动发现的 GPU”。几个标识承担不同职责：

| 标识 | 用途 | 是否应修改 |
| --- | --- | --- |
| 集群/主机 `key` | 数据库中的历史关联锚点 | 上线后不要修改 |
| `ssh_alias` | 查找 `~/.ssh/config` 中的连接配置 | 地址或跳板变化时可以修改 |
| `display_name` | 页面显示 | 可以随时修改 |
| GPU UUID | 把卡与进程样本关联 | 由厂商工具发现，不手工配置 |

状态语义如下：

- `active`：参与采集、当前统计与在线状态。
- `planned`：只做容量占位，不采集；会显示规划容量，但不进入利用率 coverage 分母。
- `retired`：停止采集并从 UI 隐藏；数据库行和已有样本保留，但当前统计与用户排行排除它。

删除 inventory 条目无法表达这些语义，也会让历史归属更难理解，因此退役应使用状态而不是
删记录。

## 存储与聚合

SQLite 使用 WAL。采集器是唯一写者并持有长连接；Web 每次查询建立只读连接，使用
`mode=ro` 和 `PRAGMA query_only=ON` 双重阻止写入。

| 数据 | 表 | 主要用途 |
| --- | --- | --- |
| GPU 原始样本 | `sample_gpu` | 当前值、近期利用率和聚合源 |
| 进程原始样本 | `sample_proc` | 当前使用人和用户 GPU·小时 |
| 主机原始样本 | `sample_host` | CPU、内存与 load |
| 5 分钟 GPU 聚合 | `rollup_gpu_5m` | 12 小时、24 小时窗口 |
| 1 小时 GPU 聚合 | `rollup_gpu_1h` | 48 小时到 1 个月窗口 |
| 1 小时主机聚合 | `rollup_host_1h` | 主机历史指标 |

聚合只处理已经封口的时间桶，并用 watermark 增量推进。常驻采集器每分钟推进 5 分钟聚合，
每 5 分钟推进 1 小时聚合，每小时执行一次保留期清理。`gpumon rollup-once` 可手工执行同一
套聚合与清理逻辑。

### 查询窗口

页面支持 `12h`、`24h`、`48h`、`72h`、`1w`、`2w` 和 `1m`：

| 窗口 | 查询来源 | 桶宽 |
| --- | --- | --- |
| `12h`、`24h` | `rollup_gpu_5m` | 5 分钟 |
| `48h`、`72h`、`1w`、`2w`、`1m` | `rollup_gpu_1h` | 1 小时 |
| 所有用户排行窗口 | `sample_proc` | 原始采样周期 |

因此 `raw_days` 必须覆盖最长的 30 天排行窗口；当前校验下限为 31 天，默认 35 天。
聚合保留期与完整配置规则见[配置参考](CONFIGURATION.md#保留天数怎么定有个坑)。

## 页面指标口径

“现在”“近期”和“所选窗口平均”是三个不同量，故意不合并：

| 页面值 | 来源与规则 | 用途 |
| --- | --- | --- |
| 瞬时值 | 每张卡最新一条原始样本 | tooltip 与单卡详情 |
| 近期利用率 | 最近 10 分钟原始样本均值；最近 3 次都 `≤5%` 时直接归零 | GPU 卡片大字、底色和在用判断 |
| 窗口平均 | 所选窗口内按样本数加权的聚合均值 | 容量规划与历史比较 |

训练负载常在步骤间出现 0/100 抖动。卡片使用近期值，可以避免把短暂间隙误判为空闲；连续
三个低样本又能让已经结束的任务快速归零。当前“在用”阈值是近期利用率 `≥10%`。

“空占”要求同时满足：该卡存在显存占用大于 0 的用户进程，且近期利用率 `<5%`。只有进程
但未占显存不算使用人；没有近期值时也不会猜测为空占。

`coverage` 比较实际样本数与“期望 GPU 数 × 窗口长度 ÷ 配置采样周期”。它用于提示掉线或
刚接入造成的数据不完整，不能把低覆盖率的均值当成完整窗口结论。

### 在线与新鲜度

当前实现保留两道独立判断：

- `/api/collector/status` 在最近成功采集不超过 **120 秒**时把主机视为在线。
- 原始样本的新鲜度上限是 `max(120 秒, 4 × poll_interval_s)`。

总览只有在主机在线且样本仍新鲜时才下发实时值和使用人；否则返回空值，而不是继续显示最后
一次陈旧占用。两道阈值目前没有统一，修改采样周期时应知道在线判断仍固定为 120 秒。

### GPU·小时

用户归属来自 `ps` 返回的操作系统用户名。每个采样时刻，同一用户在同一 GPU 上的多个 PID
先去重，再按 `poll_interval_s / 3600` 累加。若多个用户共享一张卡，每人都记完整的该段时间，
不会按人数分摊。

这个数适合观察使用趋势，不适合计费：SSH 失败会少记，实际轮次耗时与配置周期可能略有差异，
用户名也不等同于项目、作业或真实身份。

## 安全与隐私边界

生产环境建议拆成三个信任域：

| 组件 | 需要的权限 | 不应拥有的权限 |
| --- | --- | --- |
| collector / backup | SSH 配置与密钥、SQLite 写权限 | 公网入口 |
| Web | 配置和 SQLite 只读权限 | SSH home、密钥、数据库写权限 |
| Caddy / 网络层 | TLS、认证、来源限制 | 采集凭据 |

Web **没有内置登录或授权系统**。默认绑定 `127.0.0.1`；团队访问应通过带认证的 HTTPS 反向
代理，个人访问可以使用 SSH 隧道。FastAPI 文档端点生产默认关闭，昂贵查询另有并发、排队、
执行时间和返回人数边界。

公开 API 会移除 SSH alias 和 GPU UUID，但仍可能包含显示名称、主机元数据、用户名及进程名。
`mask_users=true` 只做可读性打码，不是不可逆匿名化，也不能代替访问控制。真实 inventory、
settings、SSH 配置、密钥和生产数据库都不应提交到公开仓库。
