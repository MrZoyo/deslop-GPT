# 设计

**简体中文** · [English](design.md)

`deslop` 是一套语义层面的清理规则，专门处理编程 Agent 在多轮实现和修正中不断叠加的复杂代码。Agent 实际执行的规则以独立完整的 [`SKILL.md`](../skills/deslop/SKILL.md) 为准；本文只解释背后的判断思路，不逐条复述运行指令。

## 删除优先，但不是删得越多越好

目标是只做范围明确且尽可能小的删减，在保留对外有意义行为的前提下，去掉没有充分依据的机制。删除了多少行、多少项测试或断言，以及覆盖率变成多少，都不是目标本身。

主要关注三类成组出现的问题：

1. 多轮迭代积累下来的冗余测试；
2. 形式大于实效的验证机制；
3. 过度防御和多余的回退逻辑。

常规格式化、大范围重构、框架迁移、架构重设计，以及把代码改得“更像人写的”，都不属于它的用途。

> **要精简的是测试，不是程序支持的行为。**

## 独立证据来源

一段代码是否有保留价值，要看它的依赖关系最终能否追溯到不依赖它自身的证据。有效的证据来源包括：

- 用户当前提出的需求或纠正；
- 真实存在的外部调用方；
- 对外可观察的成功、拒绝、报错或兼容行为；
- 协议、规范或持久化格式；
- 安全、权限、事务或数据损坏边界；
- 资源限制、并发约束、科学规律或数值不变量；
- 由外部独立提供的文件、清单、身份信息或预期结果。

实现看起来相似，或代码存在已久，都不能单独构成证据。代码是不是 Agent 写的、有没有测试覆盖，也同样不能。

## 相互自证的闭环

不能因为某段生产代码存在，就认定覆盖它的测试一定有保留价值；也不能因为某项测试存在，就反过来认定它覆盖的生产代码必须保留。

这种自证闭环不一定只有一对生产代码和测试，也可能包含一整串机制：

```text
产出方 → 回执 → 校验器 → 只为校验器编写的测试
  ↑                              │
  └──────── 没有外部使用者 ────────┘
```

如果这一整组代码找不到独立证据，整组都可以列为删除候选。反过来，只要存在外部使用者、协议要求、持久化边界或独立判断标准，这个闭环就被打破，相关行为必须保留。

## 生产代码与测试的不对称性

测试是程序行为的证据，却不天然拥有这个行为。由此得到两个结论：

- 重复测试或只盯着实现细节的测试可以删除，但它所观察到的程序行为仍应保持不变。
- 不能因为某项测试被认定为冗余，就顺手删除它覆盖的程序行为。

要改变程序行为，必须另外找到来自需求、调用方、规范、历史记录，或其他独立问题的证据。遇到拿不准的地方，也不应默认先补一批记录现状的特征测试。

## 验证独立性

只有当校验方拥有不同于产出方的信息、权限或故障来源时，校验才真正有价值。

以下校验应当保留：确认一份内容是否就是指定内容、核对外部提供的摘要、跨越写入与读取边界检测损坏、验证外部发布者身份，或为其他独立使用者提供保障。相反，如果校验和、回执、清单、结果封装、重复计算与校验器都在本地生成，只会重复产出方的假设乃至错误，就应进一步审查。

用了密码学术语，并不会凭空带来独立性。再强的哈希也可能只是形式大于实效的自检；一次简单的写入后回读，却可能真正跨越了故障边界。

## 回退逻辑与错误暴露

在可信代码内部，意外错误通常应该直接暴露。宽泛捕获异常后再走回退路径，常常会把内部缺陷伪装成看似合理、实际错误的结果。

如果回退逻辑实现的是文档明确规定的缺失字段处理、仍受支持的旧版本、按约定转换外部错误、失败后的清理责任或具体恢复约定，就应当保留。若它会吞掉无关异常、凭空猜一个替代值，或唯一存在理由只是有人专门为它写了测试，就值得审查。

判断依据是系统约定如何处理失败，而不是代码有没有使用 `try`/`except`。

## 科学计算与数值代码中的误报

数值检查、容差、守恒定律、求解器不变量、收敛条件、物理边界、资源限制和独立推导出的参考结果，表面上可能像防御性代码，实际上却在保护真实的科学含义。

只要数学或实验目的明确，这些检查就应保留。真正需要审查的是重复实现的计算内核、复制粘贴的公式、拿结果与自身比较的检查、元数据回执，以及无法发现任何独立数值错误的通用校验层。

## 置信度与明确保留

- **高（HIGH）：** 已完整追踪证据链，可以确认代码重复、不可达、判断恒真、只与其他代码相互自证，或已与当前有效约定脱节。
- **中（MEDIUM）：** 代码看起来没有必要，但仍缺少调用方、历史、兼容性或边界方面的证据。
- **低（LOW，默认保留）：** 涉及安全、持久化、事务、并发、外部协议、受支持的兼容行为、资源限制或科学不变量，而且其用途可能无法从局部代码看清。

`apply` 模式只处理证据已经充分的 HIGH 项；MEDIUM 的不确定性不会因为进入执行模式就自动变成删除许可。如果证据不足以支持删除，明确决定保留同样是一次成功的审查。

## 做减法，不做重新设计

默认不应新增依赖、抽象层、包装层、兼容层、来源追踪机制或替代测试。只有当少量新代码既能保留真实行为，又能换来更大且范围明确的删减时，才有理由添加。

如果一次清理反而增加了大量结构，或开始改变整体架构，就应该停下来重新确认任务边界。

## 相关方法

目标相近的项目包括 [code-humanizer](https://github.com/LeonardNJU/code-humanizer)、[agent-sh/deslop](https://github.com/agent-sh/deslop)、[dabit3/deslop](https://github.com/dabit3/deslop) 和 [ai-slop-cleaner](https://github.com/Yeachan-Heo/oh-my-claudecode/tree/main/skills/ai-slop-cleaner)。本项目的 `deslop` 有意把范围收得更窄：只处理成组累积的测试、验证和回退逻辑，而且必须同时查明哪些边界需要保留。
