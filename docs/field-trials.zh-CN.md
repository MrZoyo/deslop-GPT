# 真实项目试用

**简体中文** · [English](field-trials.md)

真实项目试用记录 `deslop` 在公开代码仓库上的实际使用过程。它用可以复核的来源与变更记录，补充合成案例和小型仓库评测；但这类材料只是历史案例，不会直接用于当前调优，也不等同于受控的基准评测。

## 方法

一次真实项目试用按以下顺序开展：

1. 将公开目标仓库固定在清理前的某个确切提交。
2. 先运行只读审计。
3. 逐项审查建议改动背后的证据链。
4. 只执行那些能从现行约定、真实调用方、历史记录和系统边界中找到依据的改动。
5. 在记录获准执行的清理时，也明确记录决定保留的内容。
6. 保存经复核的补丁和人工审核结论，仅作为参考证据。
7. 记录准确的来源提交、标签、Git 树对象 ID、许可证、采集方式和排除内容。

有充分依据的“保留”和“删除”同样有价值。一段可疑代码最终没有删除，并不一定表示清理有遗漏。

## 与 Skill 调优分离

单个仓库无法证明某种失败会反复出现，也不足以支撑一条通用的 Skill 规则。因此，真实项目案例必须与 Skill 运行时文件以及当前的定量评测集分开维护。

- 不能为了复现某次试用中经审核的补丁，反过来调整 Skill。
- 参考补丁不是唯一标准答案；未来的有效清理可以采用不同代码结构。
- 不能把单个案例中的发现扩大解释成“基准表现更好”或“精确率更高”。
- 案例可以带来新的研究问题，但不会立刻变成通用规则。

## 防止评测答案泄漏

每个案例都要把 Agent 可以看到的目标代码与参考答案材料严格分开：

```text
case/
  input/          已冻结的公开目标仓库
  reference/      经复核的补丁与人工审核记录
  README.md       材料来源、方法与局限
  manifest.json   可供程序读取的来源版本信息
```

未来如果用这些案例做评测，只能把 `input/` 复制或解包到 `deslop-GPT` 仓库之外的隔离工作区。接受评测的 Agent 只能拿到 Skill 运行文件和隔离后的目标仓库，不能看到案例目录中的 README、清单、补丁、人工审核结论或详细的预期改法。

这只是对现有案例材料如何隔离的规定，并没有新增一套评测运行程序。

### cluster-gpu-monitor 的限制

第一个案例准确记录了公开仓库清理前后的提交信息，并保存了完整的清理前文件树；但它没有从完全相同的初始状态独立运行基线。因此，这个案例不能证明 Skill 优于基线、适用于其他仓库、达到 100% 精确率，或已经过生产环境验证。

它能说明的范围更窄：可以用来复核审计建议是否准确、证据链推理是否可靠，以及面对含义不明确的行为时，Agent 是否愿意选择保留。

## 添加未来案例

未来提交新的真实项目案例时，应包括：

- 公开来源和兼容的许可证；
- 准确的清理前提交与审核后提交 ID；
- 能以相同方式重新获取的完整 Git 跟踪文件快照；
- 由 Git 生成并经人工复核的补丁；
- 简明的人工审核结论，包括决定保留的内容；
- 明确排除私有仓库、生产环境和凭据；
- 同样严格区分 `input/` 与 `reference/`；
- 在解读章节中明确说明是否存在可比的基线。

不要只为了归档一个案例，就新建评分程序、评分体系、数据结构框架或 Skill 规则。
